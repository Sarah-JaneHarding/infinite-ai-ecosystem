# T05 — the first teacher journey: a CAPS lesson draft (design)

**Status: DESIGN, 2026-11-26. Nothing in this document is built.** Audit task T05 ("deliver one complete teacher workflow") with the workflow chosen by the owner: **a CAPS lesson draft with educator review, using synthetic input.**
This note records what a read of the code found, which is more than the audit knew, and proposes the smallest honest sequence of work. It also lists the decisions that are the owner's and the steps only a named person can do.

## 1. The finding in one paragraph

A teacher cannot get a CAPS lesson draft from this system today, and the reasons are not only "no button". Seven separate things stand between a click and a safe, grounded, reviewed draft. Two of them are
silent safety gaps in code that already exists: the agent that writes lesson plans (**CE-05**) runs with its **grounding** and **template-fidelity** guardrails switched off, and it is not given the ratified material its own prompt says it
must have. Fixing the button first would hide that, so the order of work below puts the guardrails before the button.

Two further facts shape the design. The ratify scripts (`pnpm curriculum:ratify`, `pnpm templates:ratify`) ratify as a **development system actor** for dev tenants, and the script itself says production must use the principal's real identity;
so ratification in the pilot is a **human act**, not something code can do. And CE-05's own request is small: `{ grade, subject, weekNumber, termNumber, academicYear, tenantId, templateId }`, which is a natural teacher form with **no learner data in it**.

## 3. The proposed journey (for the owner to confirm)

1. **Set-up, once per subject and grade, by a person.** The HoD (or the principal) ratifies the CAPS framework and the unit blueprint for that subject and grade in L0, and the principal countersigns the school's lesson plan template. Pre-pilot this uses the existing canon ingest and ratify screens; it is not done by a script.
2. **Teacher requests.** In Teacher Studio the teacher picks subject, grade, term and week. The web route takes tenant and actor **from the verified session, never from the request body**, validates a strict Zod schema, and starts the run with the correct `gradePhase`.
3. **The worker builds the context from L0**, tenant-scoped: framework, unit blueprint and template, and **refuses** (before any model call) if any of them is unratified.
4. **CE-05 drafts**, with **all** guardrails wired: PII, age, grounding, template fidelity. The draft is stored as the requesting teacher's private draft.
5. **The teacher reviews.** The page shows the draft, the CAPS references it cites, and what it was checked against. They can edit it. Nothing is shared or "delivered" yet.
6. **Approval.** The teacher may use their own draft. Sharing it with other teachers or publishing it needs the HoD's approval (CE-05's own rule). The approval record exists before the transition commits.
7. **Everything is audited**, and the page carries no sample data and no hidden demo content.

## 6. What this design deliberately leaves out

Free-text prompts (a teacher typing a learner's name is the way a learner identifier reaches a prompt; the form here has none); LMS export and PDF/DOCX (stubs, OQ-003); learner-facing delivery; the full CE-01 to CE-09 chain in the app; and any claim about quality
beyond what the 30 CE-05 eval cases and a human reviewer show. No CAPS content, weighting or pacing is written here or in code: it comes only from the supplied, ratified sources.

## 7. How this was established, and what was not

Read from this repository at commit `42cace6` and later: contracts, the worker, the orchestrator pipelines, prompts, scripts and the source-document register. **Nothing was run.** Counts (13 agents, 30 eval cases) are from the files. I did not check
whether a producer for MOD-01 exists outside this repository, so "no entry point" means none here. The Operations platform is out of scope.
